# Bedrock-backed Blueprint diagram generation

Task 5 replaces the `/ai/diagram` stub with an on-demand Bedrock Converse call and adds a Studio action that renders its Mermaid response only after the request completes. The handler validates the documented request shape, separates the Bedrock call behind an injectable generator, reads its model and region from the Bedrock environment settings, and maps generator failures to generic 502 responses without surfacing credential errors. The browser lazy-loads Mermaid with strict security, atomically replaces the preview after a successful render, and retains the last rendered SVG when either the API or renderer fails. **Watch for:** **confirmed** server-side Mermaid validation only checks the opening declaration, so parser-invalid model output can be returned as a successful response; **confirmed** raw malformed JSON sent to the local Express endpoint bypasses the application's JSON error envelope.

**Verdict**: NEEDS_CHANGES

## High-level view

The Studio sends the exact `POST /ai/diagram` shape only when Update Blueprint is clicked. An injected generator makes contract tests independent of live AWS credentials, while production uses the configured Converse model, region, retry settings, and a Mermaid-only prompt. Credentials remain in the AWS provider chain, and the documented lack of live model access is accurately tracked as a deployment blocker.

Mermaid is lazy-loaded with `securityLevel: "strict"` and a replacement preview mounts only after rendering succeeds, so API and render failures preserve the last SVG. **confirmed** that client-side containment does not make the endpoint's 200 response truthful when Bedrock returns a `flowchart`-prefixed response that Mermaid cannot parse.

**confirmed** missing and incorrectly typed JSON values become structured 400s before Bedrock, but syntactically invalid JSON reaches different transport error paths. Lambda returns the documented JSON 400, while local Express rejects parsing before `dispatch` can create the `{ error: ... }` envelope.

## Flowchart validation ends at the declaration

**confirmed** `normalizeMermaid` strips a single outer fence and then applies only `/^(?:flowchart|graph)\b/i`. It therefore accepts `flowchart TD this is prose` and `flowchart TD\n&lt;script&gt;alert(1)&lt;/script&gt;`, despite both failing Mermaid's parser under the configured strict renderer. The contract promises that a 200 contains a valid Mermaid flowchart and that unusable Bedrock output becomes a 502. Instead, these outputs receive 200, reach the browser, and turn into a renderer failure. The last-good-preview behavior contains the UI impact, but it shifts an upstream response-validation failure into a false successful API result.

The current backend test covers prose with no flowchart declaration, so it cannot detect this boundary. Add a declaration-prefixed parser-invalid response to `ai.test.ts`, assert the generic 502 payload, and validate the full grammar before the handler produces `{ mermaid }`. Not tested: a real Converse call. The spec and coordinator explicitly record credentials and model access as blocked, so that absence is not a defect.

## Raw JSON parsing differs between local and deployed transport

**confirmed** malformed-request tests call the handler or router with already-parsed values, so they do not exercise syntactically invalid bytes. Lambda explicitly maps a failed `JSON.parse` to `400 { error: { code: "bad_request", message: "Invalid JSON body" } }`. Local `express.json()` runs before the `dispatch` catch, so its parse exception instead reaches Express's default error handler.

Add JSON-parser error middleware after `express.json()` that returns the documented 400 envelope, and cover a raw malformed-JSON request. This makes the new endpoint's local workflow conform to the same error contract as Lambda.
