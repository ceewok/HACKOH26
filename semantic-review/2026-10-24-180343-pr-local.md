# Validated solution publication and immediate confirmation

Task 6 turns `POST /solutions` from a placeholder into a validated publish boundary and connects the Studio to a post-201 confirmation page. Publication accepts only a normalized public author, a structured nonblank design spec, a known problem, and Mermaid accepted by the same conservative validator that gates Bedrock output; IDs, timestamps, and endorsement state remain server-owned. The Studio sends the current identity and last successfully rendered source, locks the action while the request is pending, and preserves the draft and preview when the request fails. The confirmation route deliberately depends on the immediate response's navigation state, leaving the reloadable public detail and gallery to Task 7. **Watch for:** No blocking concerns found in the Task 6 working-tree changes.

**Verdict**: APPROVED

## High-level view

Mermaid validation now has one conservative definition shared by generation and publishing. The server rejects both blank and nonblank invalid source before storage, so a saved solution cannot bypass the generation boundary with malformed diagram text.

The publish handler constructs the persisted record from an allowlist after confirming its problem exists. It normalizes the author by role, ignores client attempts to supply server fields, and returns storage failures without exposing repository details.

The Studio holds the rendered Mermaid source separately from mutable draft notes. It only enables publication after both are present, uses the pending state to prevent a second submission, and leaves both intact after an error.

The route at `/solutions/:id` is a Task 6 confirmation view. It displays the 201 response when navigation state exists and states that reloadable detail data, gallery access, and discussion belong to Task 7; the corresponding backend routes remain 501 placeholders.

## A single Mermaid acceptance boundary protects generation and publication

`normalizeMermaid` now owns the flowchart subset used by `POST /ai/diagram` and `POST /solutions`. The former parser-invalid nested-label regression, `flowchart TD\nA[[x] --> B`, is rejected by the generation handler with its generic 502, while `solutions.test.ts` proves that a nonblank non-Mermaid submission receives a 400 before any write. This resolves the prior mismatch in which a client could have persisted source outside the generation gate.

The validator removes an optional outer Markdown fence before checking a header plus safe edge lines. The server stores the normalized value, matching the source that the client will render under Mermaid's strict browser configuration.

## Publication owns only the fields the client is allowed to supply

The handler requires the four named spec fields to be strings and at least one to be nonblank. It retains a student's nickname and role without a supplied company, requires a nonblank company for a pro, and constructs `id`, `createdAt`, and `endorsedByPro: false` itself. The handler checks the problem before invoking `putSolution`, and its unknown-problem test proves the 404 path produces no write.

Repository exceptions become the documented generic 500 response. The handler tests cover both lookup and write failure paths, preventing DynamoDB details from crossing the HTTP boundary.

## Pending publication and confirmation preserve the Task 7 seam

The page owns `isPublishing` and supplies it to the Studio, whose button label changes to `Publishing…` and becomes disabled while the request is unresolved. The browser test drives a pending mocked request, directly checks that state, and confirms only one `api.publishSolution` call; the error-path test retains both the typed draft and rendered preview.

A successful response navigates with the returned solution as navigation state. `PublishedSolutionPage` provides only the immediate confirmation and an explicit fallback for a reloaded URL, while the registered Task 7 GET routes remain unimplemented. This avoids presenting navigation state as a substitute for the promised reloadable public detail.
