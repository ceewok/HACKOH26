# Public gallery and reloadable solution detail

Task 7 adds public solution discovery by problem, role-filtered gallery cards, and a reloadable `/solutions/:id` page rather than relying on post-publish navigation state. The backend computes direct-tweak counts across the whole problem partition before applying the requested role filter, then sorts gallery and detail tweaks newest-first. The detail page renders persisted design notes, feedback, and direct tweaks, while the seed command supplies three fixed public examples without deleting user solutions. **Watch for: possible** — mocked tests cover the handler and UI contracts, but no Docker DynamoDB Local or deployed-table read smoke test has exercised the new query paths.  
**Verdict**: APPROVED

## High-level view

The gallery is deliberately built from every solution in a problem partition before filtering. That preserves a parent blueprint's total direct-tweak count even when its children were authored by a different role, and the handler owns newest-first ordering rather than relying on DynamoDB query order.

A detail request first resolves the public solution, then loads its feedback and sibling partition to select only direct children. Both the existing Studio preview and persisted-detail preview now use the same Mermaid initialization and DOM insertion path, retaining strict Mermaid mode and avoiding HTML insertion of Mermaid source.

The seed catalog upserts fixed example IDs after reconciling problems, so repeated seeding refreshes examples without removing user-authored solutions. Task 7 remains read-only for feedback and tweaks; Task 8 and Task 9 write paths remain unimplemented.

## Role-filtered gallery preserves cross-role tweak counts

`GET /problems/:id/solutions` accepts only `all`, `student`, or `pro`; an omitted role defaults to `all`, and invalid input produces the structured 400 bad-request response. The handler builds its parent-ID count map before role filtering, so a Pro parent retains the count of a Student child in the Pro tab. It returns items newest-first by `createdAt`. Repository failures are translated to the generic load message, so DynamoDB error text does not reach the response.

## Reloadable detail exposes only direct community context

`GET /solutions/:id` returns a 404 for an unknown solution. For a known solution it keeps feedback in the repository's oldest-first order, filters same-problem solutions to `parentSolutionId === solution.id`, and sorts those direct tweaks newest-first. The page fetches this contract on mount and has distinct loading, 404, retryable-error, empty-feedback, and empty-tweak states, so a browser reload no longer depends on router state.

## Shared Mermaid path retains the trust boundary

The extracted preview module keeps Mermaid in `securityLevel: "strict"` and parses Mermaid-produced SVG as XML before replacing DOM children. Persisted Mermaid has already passed the backend's conservative flowchart validator at publication and seed-validation time.

## Seed examples and deferred write features

`solutions.json` contains two weekly-challenge examples and one peer-feedback example, with both Student and Industry Pro authors. The seed command only upserts those fixed solution records; it does not scan or remove solution records. The UI renders feedback and tweaks as read-only data and names the deferred Task 8 feedback submission and Task 9 fork-and-tweak flow without adding either write action.

## Contract coverage is mocked, not storage-integrated

Backend tests cover role validation/default behavior, cross-role counts, ordering, direct-only tweaks, 404, and generic repository-failure responses. Frontend tests cover gallery filter refetching, retryable errors, empty states, detail reload behavior, Mermaid rendering, feedback, and tweak links. Not tested: a transport-level GET against DynamoDB Local or AWS, including the TypeIndex filtered lookup used to resolve a solution ID.
