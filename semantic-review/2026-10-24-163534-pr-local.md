## High-level view

The reconciliation makes catalog replacement a two-phase operation: desired entries write first, and only a successful write phase can identify old IDs for retirement. This preserves the old catalog when source parsing, validation, or an upsert fails, while a completed weekly-ID replacement has one active weekly metadata record.

The repository queries only `type = "problem"` records and deletes only the corresponding `PROBLEM#<id>/META` item. In this Task 2 codebase, `putProblem` has no production caller outside the seed script, so the ownership boundary matches the seeded-only model rather than deleting an independent author-managed Problem.

## The seed source now replaces retired weekly IDs

`syncSeedCatalog` writes every validated source entry before it asks the store for existing problem IDs. It then subtracts the desired IDs and calls `remove` only for the remainder. After a replacement weekly record writes, the old weekly ID appears in `removed` and its metadata record is deleted.

```text
seed/problems.json
       │ validate: unique IDs, exactly one weekly record
       ▼
write every desired PROBLEM#<id>/META
       │ all writes succeed
       ▼
list TypeIndex records where type = problem ──► remove IDs absent from source
```

Invalid JSON, an invalid catalog, or a failed desired write prevents the list-and-remove phase from running, so a failed reseed does not erase the existing catalog. `listProblemIds` reads only `type = "problem"`, and `deleteProblem` targets only that record's `META` key. The project currently creates its Problem catalog exclusively through `seed.ts`; `putProblem` has no other production caller. **Confirmed:** this makes source-authoritative deletion safe for the Task 2 seeded-only Problem catalog.
