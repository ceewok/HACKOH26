# Seeded problems API with local DynamoDB support

Task 2 expands the catalog to one weekly challenge and six persistent problems, validates the seed source, and exposes the weekly-first Hub list plus full problem detail described in §4. The persistence layer now queries the type index for lightweight list records, and the handlers convert DynamoDB failures into the specified generic 500 response. Local DynamoDB receives explicit dummy SDK credentials only when an endpoint is configured, so normal local setup does not need AWS credentials. **Watch for:** **confirmed** replacing or removing a seeded weekly ID leaves the old DynamoDB item in place, so an already-seeded table can return multiple weekly challenges; **confirmed** the DynamoDB Local table/seed/API smoke has not run because Docker Desktop is unavailable, although the documentation accurately identifies it as pending rather than tested.

**Verdict**: NEEDS_CHANGES

## High-level view

The API separates Hub summaries from full problem records at the repository boundary. The list result contains only `id`, `title`, `hook`, and `isWeekly`, with weekly records ordered first; detail returns the contract's description, constraints, and hint pills. Storage failures use a generic error instead of exposing DynamoDB connection data.

The seed source enforces one weekly record, unique kebab-case IDs, and non-empty display content before writing. Its upsert model safely repeats writes for existing IDs, but it does not synchronize deletions, so the source invariant does not hold after a weekly entry is replaced with a new ID.

The local setup supplies placeholder credentials only with `DYNAMODB_ENDPOINT`, and the table script refuses to run without that endpoint. Docker's engine is confirmed unavailable on this machine, so the documented integration gap remains real rather than being presented as a completed smoke test.

## Retired seed items can violate the weekly invariant

`validateCatalog` confirms that the JSON input contains exactly one weekly entry, and `seedProblems` invokes the writer once for each input record. In production, that writer is `putProblem`, which issues a `PutCommand` at `PROBLEM#<id>/META`; it has no operation that discovers or deletes catalog records omitted from the revised JSON.

For example, a local table seeded with `weekly-live-office-hours` will retain that item if a future catalog removes it and adds a different weekly ID. The revised JSON passes validation, but the type-index query returns both records and the Hub gets two `isWeekly: true` summaries. Make the seed operation reconcile its previously managed problem keys, or document and provide a safe reset command for catalog replacements. Add an integration-level test covering a removed weekly ID and a new weekly ID.

## Docker-blocked table and HTTP smoke

`docker info` could not connect to Docker Desktop's Linux engine, so no real DynamoDB Local table was created during this review. The passing tests verify catalog validation, map-based upsert behavior, handler response shapes, blank/unknown IDs, and generic list storage errors; they do not exercise the TypeIndex query, local credentials, table definition, or HTTP transport against DynamoDB Local.

This limitation is clearly and consistently documented. `docs/specs/bridge-builder.md` labels the real table/seed/API smoke as blocked, and `agents/sync-coordinator.md` records Docker's unavailable engine and keeps the smoke test pending rather than claiming it passed. Once Docker is running, execute `npm run db:setup`, `npm run seed`, start the backend, and smoke `GET /problems` plus both a known and unknown detail ID.
