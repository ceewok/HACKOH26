# Persisted Industry Pro session validation in the Hub

Task 3 now treats the locally persisted demo identity as untrusted input before it decides whether to show onboarding or the Hub. `session.ts` trims the nickname and, for an Industry Pro, the company; a malformed record, a missing company, or a blank company produces no session and reopens onboarding. The onboarding form enforces the same requirement before persistence, while the Hub continues to fetch only `GET /problems` summaries through `api.ts`, select its weekly card by `isWeekly`, and route cards to the Task 4 placeholder. The full suite passes: 11 backend contract tests and seven frontend browser tests, including the missing-company persisted-Pro regression. **Watch for:** **confirmed · low** the regression test exercises a persisted Pro record with no `company` property, but does not explicitly assert the empty-string or whitespace-only company cases that the new normalization code rejects. **confirmed · validation limitation, not a code defect** Docker Desktop's Linux engine is unavailable, so the populated Hub has not been smoke-tested against DynamoDB Local.

**Verdict**: APPROVED

## High-level view

Session parsing is now the gate between browser storage and the authenticated-looking UI state. A persisted Pro record cannot reach the Hub unless its trimmed nickname and company are both present; `setSession` also applies the same normalization before it writes a new record. The role remains a deliberately local, unauthenticated demo identity, as specified, rather than a server-side authorization claim.

The onboarding route, Hub, and problem destination retain a simple path through the existing API seam. An absent or rejected session holds the visitor on the landing state behind the onboarding dialog, while a valid session supplies the Hub identity and enables `/problems/:id`; problem summaries still carry only the published list contract.

The frontend suite reaches the repaired missing-company stored record, the onboarding flow, Hub data states, and card navigation. **Confirmed · low:** raw local-storage values with `company: ""` or whitespace have no direct assertions, even though normalization rejects them. Docker's unavailable engine affects only a real local-data smoke, not the browser, contract, or type validation that passed here.

## Persisted Industry Pro identities now fail closed

`getSession` parses local storage only through `normalizeSession`. That boundary rejects nonobjects, malformed JSON, empty nicknames, unknown roles, and Pro records whose trimmed company is absent or empty. It returns `null` instead of allowing a partial identity into `App`, so a stale persisted Pro record falls back to required onboarding rather than displaying an Industry Pro Hub state without a company.

The write path applies the same normalization. `setSession` throws before writing an invalid record, and `OnboardingModal` validates its trimmed fields before it calls that API. This creates one persisted shape for Pro identities regardless of whether they were restored or freshly entered.

```text
localStorage
    │ getSession → normalize nickname, role, and Pro company
    ├── invalid / incomplete ──► Landing state + onboarding dialog
    └── valid Session ─────────► Hub(session) ─► api.listProblems()
                                              └► /problems/:id placeholder
```

The session unit test now restores `{ role: "pro", nickname: "Ada" }` and observes `null`, directly exercising the defect that let a stored Pro session through without a company. **Confirmed · low:** it does not cover records that include a company key but make it empty or whitespace-only. Those values reach the same falsey return in the current implementation, but direct tests would protect the trimming requirement rather than only the missing-key variant.

## Onboarding, Hub state, and card routes stay on their published boundaries

The modal requires a nickname for either role and a company for Pros, persists the trimmed identity, and completes into the session state held by `App`. Resetting the profile clears storage before reopening onboarding. When no session is accepted, the root route does not invoke the Hub request; when a session is accepted, `HubPage` renders its identity-specific heading and role label.

The Hub imports `ProblemSummary` and calls only `api.listProblems()`. It finds the weekly card by `isWeekly`, keeps all other list entries in the persistent grid, and keeps loading, empty, and retryable API errors in the same view. Each card encodes its ID for `/problems/:id`, where the deliberate Task 4 placeholder replaces the former missing destination. The App browser test follows onboarding through a rendered weekly card to that route, and the Hub tests mock the established API seam with the published `{ id, title, hook, isWeekly }` shape.

## Browser validation is complete except for the raw empty-company variants

`npm test` passed all 11 backend tests and all seven frontend tests. The frontend cases cover a valid persisted Pro identity, malformed/incomplete storage, form-level Company validation and trimming, the onboarding-to-Hub flow, weekly and persistent card rendering, API error retry, and selected-problem navigation. `npm run typecheck` also passed for both packages.

**Not tested:** a persisted Pro session whose `company` field is `""` or consists only of whitespace. This is a narrow coverage gap, not a reproduced code failure: `normalizeSession` trims the field and returns `null` in both cases. Add those direct storage values to `session.test.ts` alongside the missing-company record.

## Docker's unavailable engine is a separate integration limitation

`docker info` reaches the Docker client but cannot open `//./pipe/dockerDesktopLinuxEngine`, so DynamoDB Local cannot currently provide the seeded `GET /problems` response to a running SPA. The frontend tests substitute `api.listProblems` at the existing seam, while backend contract tests cover the response shape. **Confirmed · validation limitation, not a code defect:** this prevents only the real populated-Hub smoke; it does not indicate a Task 3 regression.
